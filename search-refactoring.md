## 0. Резюме

**Что есть.** Поиск по активным сайтам (до 13 из 23 известных; по умолчанию у нового пользователя — первые 13 в порядке реестра) работает параллельно, результаты появляются по мере ответов, запрос можно отменить и повторить. Это добротный каркас (`search/SearchSession`, `ProviderPage`, `SiteHttp`), покрытый тестами. Но пользовательский результат слабый: одна книга с пяти сайтов показана пять раз, порядок — порядок прихода ответов, статусы источников не видны до самого конца, после закрытия экрана или смерти процесса всё ищется заново, нет сортировки, нет области поиска (название / автор / чтец / цикл), медленный сайт держит спиннер до 45 секунд, а с повтором в другом регистре — почти до полутора минут.

**Что предлагается.** Не менять стек и каркас, а достроить над ним четыре вещи:

1. **Видимое состояние каждого источника** — чипы источников под строкой поиска становятся индикаторами: значок, цвет, число найденного, повтор одного источника; «Все» агрегирует (зелёный / жёлтый «с ошибками» / индикатор «ответили 7 из 13» в процессе). Состояние уже есть в `SearchSession.statuses()`, его просто не доносят до интерфейса.
2. **Пост-обработка результатов на устройстве** — чистый, тестируемый модуль: нормализация → соответствие слов запроса словам полей карточки (наибольшего веса, венгерский алгоритм) → детерминированная оценка → группировка одинаковых произведений и их озвучек → сортировка (по соответствию по умолчанию; название, автор, чтец, длительность по выбору) в трёх представлениях (произведения / озвучки / карточки) → надёжность предложения (фрагмент LitRes, удалённая книга) по признакам карточки, профилю сайта и памяти о проверенных книгах. Два портированных алгоритма из `java-string-similarity` (OSA для опечаток в словах, Sørensen–Dice по биграммам для похожести названий), около 100 строк, без новой зависимости.
3. **Область поиска и профили источников** — переключатель Везде / Название / Автор / Чтец / Цикл; каждый адаптер декларирует профиль поиска (что индексирует сервер, есть ли поиск людей, минимальная длина запроса, регистрозависимость, число запросов в операции, ожидаемая скорость, порядок выдачи). Планировщик по профилю решает, какой путь слать сайту, что отфильтровать локально и какой единственный резервный шаг сделать при пустом ответе. Семьи зеркал (Книгоблуд–Библус–Голосом, Akniga–Golosknig) показываются одним предложением; «один запрос на семью» — настройка, не умолчание.
4. **Снимок последнего поиска** — результаты, статусы, курсоры и позиция живут в памяти процесса и в файле; повторный вход показывает их мгновенно, с кнопкой «Обновить». Плюс кеш ответов: смена вкладки, сортировка, возврат — ноль HTTP.

**Порядок.** Сначала пять ошибок P0 (один PR, низкий риск), затем статусы источников, затем стабильный список, снимок и секция «В библиотеке», затем короткий измерительный прогон, затем ранжирование и сортировки, затем группировка, затем область и профили вместе с режимами «Авторы/Чтецы» экрана, в конце — отменяемый транспорт, бюджеты времени (T09) и зеркала. Каждый этап самостоятельно полезен и обратим (§11).

**Ожидаемый эффект.** Для слушателя: ответ на «есть ли эта книга и где её лучше слушать» за один взгляд, а не за прокрутку 60 карточек; видно, кто ещё ищет и кто упал; второй вход в поиск бесплатный. Для кода: пост-обработка и планировщик — чистые функции с тестами на фикстурах; сетевой каркас не трогаем до этапа T09.

### 1.2. Режимы экрана

`SearchableActivity` — один экран на три роли, и переработка обязана сохранить все:

| Режим (`Consts.ARG_MODEL`) | Кто открывает | Что ищет | Что делает с результатом |
|---|---|---|---|
| `MODEL_BOOKS` | кнопка поиска в каталоге и избранном (`BooksFragment.showSearchActivity`, `FavoriteFragment`), голос (`MediaPlayerService.onPlayFromSearch`) | книги по всем активным источникам + чипы авторов/циклов | тап по книге открывает `BookActivity` поверх поиска (поиск остаётся под ней); тап по чипу автора/цикла или пункту долгого нажатия — `returnResult(url, name, …)` → `setResult` + `finish()`: поиск **закрывается**, `MainActivity` показывает `BooksFragment` автора |
| `MODEL_AUTOR` / `MODEL_ARTIST` | разделы «Авторы»/«Чтецы» каталога | людей **одного** текущего источника (`startGenreSearch`, `SearchSession<GenrePOJO>`) | `returnResult` → список книг человека в каталоге |
| `MODEL_GENRE` | — | список без пагинации | то же |

Следствие для документа: новый экран должен уметь показывать плоский список сущностей (`GenrePOJO`) и возвращать результат вызывающему; эти режимы либо сохраняются как есть до этапа 5, либо поглощаются областью «Автор»/«Чтец» (§10.5).

### 1.4. Что уже сделано правильно и что нельзя сломать

- Поколения (`generation`): новый запрос отменяет подписки прежнего, поздние ответы игнорируются (тесты `lateResultsOfASupersededQueryAreIgnored`, `aLateAnswerOfTheSupersededRun…`).
- Ошибка — значение (`ProviderPage.failed`), а не исключение; статусы OK / EMPTY / ERROR / TIMEOUT / BLOCKED; challenge-страницы (Cloudflare, DDoS-Guard) распознаются в `SiteHttp.parse`.
- Независимые курсоры страниц по источникам; защита от сайта, повторяющего последнюю страницу; страница, у которой все карточки отфильтрованы парсером, не останавливает источник (`ProviderPage.of(items, hasMore, rawCards)`).
- Презентер переживает поворот (Moxy хранит его в `PresenterStore`, `@ProvidePresenter` вызывается только при отсутствии; `showDataBooks` со стратегией `AddToEndSingle` возвращает список после поворота). Отмена при уходе с экрана с одновременным скрытием прогресса (SRCH-08); «не найдено» только при полном завершении без ошибок (`isNotFound`).
- Единая точка HTTP (`SiteHttp`): user agent, Accept-Language, cookie jar по хостам, лимит тела 4 МиБ, POST-страницы Audioboo, учёт прокси по сайтам (`AppProxy`).
- Реестр `Provider` как единственное место «всего, что не парсинг» про сайт; зеркала уже описаны данными (`mirrorOf`).

Инварианты, которые переработка сохраняет: один адаптер = один класс, парсеры — чистые функции над `Document`/JSON, тестируемые на фикстурах; идентичность сохранённой книги — её канонический URL (избранное, история, загрузки); `sourceId`, папки загрузок и `prefKey` не меняются; `BooksListAddapter` используют каталог и избранное — его контракт для них не меняется.

## 2. Глазами слушателя: сценарии и боли

Восемь сценариев реального использования. В каждом — что происходит сейчас и что должно происходить. Это функциональное задание; §5–9 объясняют, как его выполнить.

| № | Сценарий | Сейчас | Должно быть |
|---|---|---|---|
| S1 | **Конкретная книга**: «мастер и маргарита» | 40–70 карточек вперемешку по сайтам; одна и та же озвучка Клюквина с четырёх сайтов — четыре карточки; надо листать и сравнивать глазами | Одна группа «Мастер и Маргарита — Булгаков», в ней озвучки (по чтецу и версии записи), у каждой — список сайтов; лучшее совпадение сверху; тап по озвучке открывает книгу на предпочтительном сайте |
| S2 | **Автор + название**: «булгаков собачье сердце» | Сайты «только название» (ABMP3, База Книг, Lis10book; Audiokniga-online автора не индексирует) возвращают пусто; пустые сайты не отличимы от упавших; Lis10book выручают подсказки, остальные — нет | Таким сайтам один резервный запрос без фамилии (подсказка от соседей, §7.3); локально проверяется, что фамилия совпала с автором; чип сайта честно показывает «0», а не молчит |
| S3 | **По автору**: «Лукьяненко» | 13 списков по 10–50 карточек, где фамилия встречается где угодно (на Aknig.xyz в выдаче книги Каганова и Ткаченко); чипы авторов — с двух сайтов | Область «Автор»: карточки, где Лукьяненко — автор; группировка по произведению; сверху строка «Авторы» со всех сайтов, где есть поиск людей (у нового пользователя их 4, с включёнными Aknigi24, Lis10book, Audiokniga.one — 7), с переходом на страницу автора |
| S4 | **По чтецу**: «Князев» | Поиск по тексту; чтец в названии не встречается, сайты отвечают почти пусто или мусором; Голосом один ищет по чтецу | Область «Чтец»: поиск чтецов на сайтах, где он есть; книжный поиск с локальной проверкой поля «чтец»; карточки без чтеца (Slushat-knigi) — в свёрнутой секции «без данных о чтеце», а не потеряны |
| S5 | **Цикл**: «Дозоры» | Циклы только с Книги в ухе; книги цикла растворены среди прочего | Область «Цикл»: поле «цикл» карточки; «Тайна Ночного дозора» не выше книг цикла |
| S6 | **Повторный вход**: ушёл в плеер, вечером снова открыл поиск; нажал чип автора и вернулся; процесс убит системой | Всё заново: 13 запросов, 5–45 с ожидания, список прыгает. (Поворот и возврат из `BookActivity` выдачу **не** теряют — Moxy и стек Activity её держат) | Снимок последнего поиска показан мгновенно с подписью «Результаты от 14:20» и кнопкой «Обновить»; вкладка и позиция восстановлены |
| S7 | **Медленная сеть / упавший сайт** | Спиннер до 45 с без объяснений, с повтором регистра — дольше; одна строка «2 источника недоступны» в конце; «Повторить» перезапрашивает всех упавших | Через 2 с: «ответили 6 из 13»; долго отвечающие чипы помечены ⏱; упавшие — красным, повтор по чипу; «Все» жёлтый: «48 книг · не ответили: Библус, Голосом» |
| S8 | **Голосовой поиск / Android Auto / TV** | Запрос приходит через `ACTION_SEARCH`; на TV `retrySources` отсутствует в разметке → NPE в `onCreate` | То же, что на телефоне, без исключений; на TV статусы читаются без цвета (значок + подпись), фокус D-pad идёт по id |

Общее требование: **ни один результат не должен исчезать из-за переработки** — группировка обратима («показать все карточки»), фильтр области ослабляется явным действием, упавший источник всегда можно повторить.

## 4. Целевая концепция и принципы

1. **Единица результата под вкладкой «Все» — произведение, а не карточка сайта.** Группа «произведение → озвучки → сайты». Во вкладке сайта — плоский список его карточек. Группировка обратима одним действием.
2. **Состояние каждого источника видно всегда**: в очереди, ищет, ответил (сколько), пусто, долго отвечает, таймаут, ошибка, ограничение частоты, заблокирован, пропущен (и почему), из снимка.
3. **Запрос имеет область**: Везде / Название / Автор / Чтец / Цикл, можно несколько. Область исполняется серверным путём там, где сайт его имеет, и локальной проверкой везде; строгость ослабляется только явным действием; ограниченная полнота на сайтах без такого пути называется прямо.
4. **Порядок детерминирован и объясним**: оценка по словам и полям, стабильные разрывы связей, пояснение «совпали название и автор». Никаких нечётких сравнений в компараторе.
5. **Ничего не теряется и ничего не повторяется**: снимок последнего поиска; кеш ответов; смена вкладки, сортировки, группировки, возврат — ноль HTTP.
6. **Время — три независимых лимита** (HTTP-попытка, операция источника из профиля, абсолютный предел прохода), и интерфейс не ждёт самого медленного: показывает прогресс, помечает долгих, предлагает остановить ожидание.
7. **Честность статусов**: пустой ответ — успех с нулём; таймаут — не ошибка навсегда; «не найдено» — только когда все ответили; неполный проход — жёлтый, не зелёный.
8. **Минимум новых сущностей**: пост-обработка и планировщик — небольшие чистые классы в пакете `search/`; адаптер получает одну декларацию профиля; никакого фреймворка, второго сетевого стека или Room-миграции на первом этапе; две новые настройки, не больше.

## 5. Модель запроса и область поиска

### 5.1. `SearchRequest`

```
SearchRequest {
  text:   String                    // как ввёл пользователь, trim
  scope:  EnumSet<Field>            // ∅ = Везде; иначе подмножество {TITLE, AUTHOR, READER, SERIES}
}
Field { TITLE, AUTHOR, READER, SERIES }
```

Семантика области: карточка подходит, если **каждое значимое слово запроса** найдено **в каком-нибудь из выбранных полей** (И между словами; ИЛИ между полями на уровне слов). «Везде» = все четыре поля, и разные слова ложатся в разные поля («булгаков» → автор, «собачье сердце» → название); «Автор» = все слова в поле «автор»; «Автор, Чтец» = каждое слово либо в авторе, либо в чтеце. Это ровно то, что считает алгоритм A.2 с ограничением набора полей, так что формулировка и реализация совпадают. Расширенный режим с отдельными полями через И (Codex §5) не нужен на первом этапе: распределение слов по полям покрывает основные случаи; позже его заменят чипы уточнения «Автор: Булгаков ×» по тапу на карточке (§11, идеи на потом).

### 5.2. Как область исполняется

| Область | Серверный путь | Локальная проверка |
|---|---|---|
| Везде | книжный поиск с полным текстом; у сайтов «только название» при пустом ответе — один резервный шаг (§7.3) | распределение слов по полям, оценка (§6.2) |
| Название | книжный поиск; у сайта с `titleOnlyParam` (Audiokniga-online) — путь «только название», если область стояла в момент отправки | все слова в поле «название» |
| Автор | книжный поиск **плюс** поиск людей (`AUTHORS`) там, где он есть → строка «Авторы» (сущности, не книги: книги автора открываются тапом, автоматически не догружаются — иначе N+1) | все слова в поле «автор»; карточка без автора → UNKNOWN |
| Чтец | книжный поиск **плюс** поиск людей (`PERFORMERS`) → строка «Чтецы» | все слова в поле «чтец»; без чтеца → UNKNOWN |
| Цикл | книжный поиск | все слова в поле «цикл»; без цикла → UNKNOWN |
| несколько | книжный поиск + поиск людей для каждой выбранной людской области | ИЛИ по выбранным полям |

**UNKNOWN не выбрасывается.** Карточки без проверяемого поля (Slushat-knigi не отдаёт чтеца и цикл, ABMP3 — цикл и длительность, Golosknig — цикл) собираются в свёрнутую секцию «Без данных о чтеце (N)» внизу. Это принцип Codex §5, с ним согласны: иначе область «Чтец» молча теряет часть каталога.

**Полнота честно ограничена.** На сайте «только название» область «Автор» не создаст кандидатов, которых сервер не вернул: локальная проверка фильтрует полученное. Чип такого сайта в людской области получает подпись «по карточкам» (contentDescription «…проверено по полученным карточкам, поиск по автору на сайте недоступен»), сводка — «на 4 сайтах поиск по автору ограничен».

### 5.3. Ввод области в интерфейсе

Кнопка области в тулбаре справа от строки поиска: иконка воронки с подписью под ней, где хватает ширины («Автор»), и с точкой-бейджем на узких экранах; на ширине 360 dp текстовая кнопка «Автор, Чтец ▾» сжала бы поле ввода. Текущая область **всегда видна текстом** в строке сводки («область: Автор»), чтобы забытый фильтр не объяснял потом «почему ничего не нашлось». Нажатие открывает меню с отмечаемыми пунктами `Везде` `Название` `Автор` `Чтец` `Цикл`: несколько — ИЛИ, «Везде» снимает остальные. Область запоминается в истории вместе с текстом и в снимке (§8); голосовой запрос (`ACTION_SEARCH` из `MediaPlayerService`) всегда идёт с областью «Везде» — голос смешивает автора и название.

Смена области при загруженных результатах **не делает новых книжных запросов**: книжный запрос одинаков при любой области (`SearchUrls.Category` знает только BOOKS / AUTHORS / PERFORMERS); пересчитываются оценка и фильтр. Запросы уходят только за новым путём — поиском людей для «Автор»/«Чтец». Единственное исключение — сайт с `titleOnlyParam`: если запрос отправлялся в области `{Название}` его особым путём, расширение области даёт этому сайту один новый книжный запрос обычным путём (чип возвращается в «ищет»), иначе кандидаты, отсечённые сервером, не вернулись бы. Ключ кеша ответов (§8.4) включает фактический URL, так что ответы двух путей не смешиваются.

### 5.4. Разбор текста запроса

Текст делится на слова после нормализации (§6.1). Специального синтаксиса (кавычки, минус, `автор:`) не вводим: аудитория — друзья владельца, а область даёт то же без обучения. Единственная эвристика — « — » / « - » между частями («Стивен Кинг — Оно», как `OtherSourceModel.withoutAuthor`): левая часть — подсказка «автор», правая — «название», оценка получает небольшой бонус за такое распределение. Ничего не отбрасывается.

## 6. Пост-обработка: нормализация, оценка, группировка, сортировка

Весь раздел — чистые функции без Android и сети (`search/TextNorm`, `search/StringSim`, `search/SearchMatcher`, `search/SearchGrouper`, `search/SearchOrder`), работающие на `Schedulers.computation()` над неизменяемыми снимками списка. Вход: предложения (`Offer`: `BookPOJO` + источник, страница, позиция на странице). Выход: отсортированные группы с оценками. Нормативный псевдокод — Приложение A; таблицы ниже его пересказывают, при расхождении прав псевдокод.

### 6.1. Нормализация

`TextNorm.key(s)` — одна форма для поиска и группировки:

1. Unicode NFC; нижний регистр через `Locale.ROOT`; `ё → е`; `й` остаётся.
2. Латинские буквы-двойники (`a c e o p x y`) в слове, где остальные буквы кириллические, сворачиваются в кириллицу (сайты и пользователи путают раскладку в одной букве).
3. Любая пунктуация и символы (Unicode-классы `\p{P}` и `\p{S}`, не ASCII-`\p{Punct}`), включая кавычки, тире, дефисы, скобки, `№`, апострофы, и любые пробельные символы, включая NBSP (`UNICODE_CHARACTER_CLASS`), → один пробел; trim. «Салтыков-Щедрин» → два слова, и для ключа имени дополнительно порождается слитная форма.
4. Цифры и слова «том 2», «часть 1», «книга 3» **не удаляются**: они участвуют в оценке и запрещают слияние томов.
5. Стоп-слова не удаляются («Мы», «Оно», «И никого не стало» — это названия), но в **покрытии** (§6.2) считаются только значимые слова: числа (всегда — «том 2» обязан совпасть) и слова длиной ≥ 2 не из короткого списка служебных (`и в на с о а у к по из за не от для the of a and`); если значимых слов нет, значимы все.
6. **Издание** отделяется от названия до вычисления ключа: только распознанные маркеры версии записи (`полная версия`, `сокращ…`, `спектакль`, `радиоспектакль`, `радиопостановка`, `аудиоспектакль`, `инсценировка`, `фрагмент`, `отрывок`, `с музыкой`) и скобочные группы, которые их содержат, уходят в поле `edition`; «(том 1)», «(сборник)», подзаголовки остаются в `normTitle`. Издание делит **озвучки**, а не произведения (§6.4).
7. **Имена людей.** Строка авторов/чтецов делится на людей по `,`, ` и `, `&`, `/`, `;`; «и др.» отбрасывается. Для каждого человека: слова имени без инициалов (≤ 2 букв) и отчеств (окончания `-ович -евич -ьич -ич -овна -евна -ична -ьевна`); **ключ человека** — отсортированное множество этих слов целиком (не префиксов и не «самое длинное слово»: «Стивен Кинг» = «Кинг Стивен» = `{кинг, стивен}`; «Александр Клюквин» ≠ «Александр Котов»; «Котов» ≠ «Котова» — это разные люди, окончания не прощаются). «Тот же человек» в нечётком шаге группировки — множество слов одного **входит** в множество другого и инициалы не противоречат (`{булгаков}` ⊂ `{михаил, булгаков}`; «М. Булгаков» → инициал `м` совместим с «михаил»).
8. Транслитерация, раскладка целиком, стемминг, Jaro–Winkler для имён — не на первом этапе (§13).

Поля карточки нормализуются один раз при приходе и кешируются в `Offer`, а не при каждой сортировке. Пределы: ≤ 12 слов запроса, ≤ 24 слова на поле, ≤ 1500 предложений в сессии (дальше — «Искать дальше» отключается с подписью).

### 6.2. Соответствие и оценка

Три уровня качества слова, фиксированные веса полей, покрытие и два бонуса — детерминированное число 0–100 и объяснимый уровень A–E, совместимый с уровнями Codex §6.

**Качество совпадения слова `t` запроса со словом `w` поля:**

| Условие | Качество |
|---|---|
| `w == t` | 1.00 |
| `w` начинается с `t`, `len(t) ≥ 4` (не закончен набор, падеж: «дозор» → «дозора») | 0.90 |
| `OSA(t, w) == 1`, `len(t) ≥ 5` (опечатка, перестановка соседних букв) | 0.80 |
| `OSA(t, w) == 2`, `len(t) ≥ 9` | 0.65 |
| `t` — число: только `w == t` | 1.00 / 0 |
| иначе | 0 |

OSA (Optimal String Alignment, ограниченный Дамерау–Левенштейн) считает перестановку соседних букв одной правкой — типичная опечатка на телефоне. Ранний выход при разнице длин > 2 отсекает большинство пар без матрицы.

**Веса полей** («Везде»): название 1.00, автор 0.95, цикл 0.90, чтец 0.90. В области с выбранными полями участвуют только они, вес 1.00.

**Соответствие слов запроса словам полей** — соответствие наибольшего веса в двудольном графе «вхождение слова запроса — слово поля» с рёбрами `качество > 0` (слово поля используется один раз; повторы в запросе — отдельные вхождения). Вес ребра = `1000 + round(100 · качество · вес поля)`: тысяча делает число пар главным критерием, остаток — суммарное качество среди соответствий одинаковой мощности. Решается венгерским алгоритмом (Куна–Манкреса) на матрице ≤ 12 × 96, равенства разрешаются порядком полей название, автор, цикл, чтец и индексом слова. Так «алекс алексей» против «Алексей Александров» покрывает оба слова (жадность теряла одно), а «дозоры дозор» против «дозоры дозора» берёт точное + префикс, а не опечатку + префикс. ~60 строк; микросекунды.

**Оценка предложения:**

```
sig      = значимые слова запроса (§6.1 п.5); n = |sig|
coverage = |{t ∈ sig : сопоставлено}| / n
base     = Σ_{t сопоставлено} quality(t) · weight(field(t)) / |все слова запроса| · 100
bonus    = +8  если |все слова| ≥ 2 и все сопоставленные лежат подряд и по порядку в одном поле (фраза)
           +10 если нормализованное поле целиком равно нормализованному запросу (один раз)
           +3  если распределение совпало с подсказкой «Автор — Название» (§5.4)
score    = min(100, round(base + bonus))
```

**Уровень** (одно определение, A.2 нормативен):

| Уровень | Условие | Что видит пользователь |
|---|---|---|
| A | нормализованное поле целиком равно нормализованному запросу (в «Везде» — любое поле; в области — одно из выбранных) | «точное совпадение» |
| B | `coverage == 1`, все качества 1.0, фраза в одном поле | «совпало название» / «совпал автор» |
| C | `coverage == 1`, все качества 1.0, порядок и поля любые | «совпали название и автор» |
| D | `coverage == 1`, есть префикс или опечатка | «похоже: „серцде“ → „сердце“» |
| E | `coverage < 1` | свёрнутая секция «Похожие (N)», когда есть хоть одно A–D; иначе — в списке с пометкой «частичное совпадение» |

Служебные слова не влияют на уровень: «гарри поттер и философский камень» против карточки «Гарри Поттер. Философский камень» (без «и») — покрытие 4/4 значимых, уровень C, а не E. Внутри уровня при однословных запросах оценки часто равны — порядок решают следующие ключи сортировки (§6.5), это нормально.

**Шумные источники.** Для карточки с `FULLTEXT`-сайта (Audiokniga.one, Audiokniga-online) уровень E означает «совпало в аннотации» — такие карточки не поднимаются выше секции «Похожие» (ответ на W20 без знания текста аннотации).

**Процент.** Оценка хранится как целое 0–100 для сортировки. На карточке по умолчанию — не число, а причина уровня («совпали название и автор»): 87 против 84 не отличимо на слух и читается как точная вероятность. В настройках — «Показывать оценку соответствия»; в долгом нажатии — «Почему здесь: название 100, автор ✓». Согласие с Codex §6: не называть это вероятностью или процентом.

### 6.3. Какие алгоритмы портировать и почему не зависимость

Из `tdebatty/java-string-similarity` (MIT, Java 8) берём два класса и переписываем компактно в `search/StringSim.java` (~100 строк, уведомление MIT в заголовке файла):

| Алгоритм | Зачем | Где |
|---|---|---|
| **OSA / ограниченный Дамерау–Левенштейн** | опечатки и перестановки букв в слове запроса (§6.2) | `SearchMatcher` |
| **Sørensen–Dice по биграммам символов** | похожесть целых названий при слиянии групп, устойчива к порядку слов и мелким различиям: «Мастер и Маргарита» / «Мастер и Маргарита полная версия» ≈ 0.7 (не сливаем — и издание уже отделено на §6.1 п.6); «Собачье сердце» / «Собачье сердце.» = 1.0; «Дюна» / «Мессия Дюны» ≈ 0.3 | `SearchGrouper` |

Jaro–Winkler из черновика исключён: для имён он прощает окончания («Котов» / «Котова»), а это разные люди; имена сравниваются множествами слов (§6.1 п.7). Не берём также Cosine / Q-Gram (то же, что Dice, дороже), N-Gram, LCS, SIFT4, Weighted Levenshtein.

Почему порт, а не `implementation 'info.debatty:java-string-similarity:2.0.0'`: нужны 2 класса из 15; библиотека не обновляется и тащит `jcip-annotations`; правило проекта — компактный код. Release/R8-проверка нужна в обоих случаях (новый код в пост-обработке проверяется release-сборкой так же, как любая зависимость). Если владелец предпочитает зависимость — алгоритмы те же (§14).

### 6.4. Группировка

**Модель данных:**

```
Offer     { book: BookPOJO, source: Provider, page: int, rank: int,
            norm: {title, edition, authors: Set<PersonKey>[], readers: Set<PersonKey>[], series, durationMin?},
            score, tier, assigned, firstSeen: long }
Group     { id: String, key: GroupKey, title, authors, offers: List<Offer>, narrations: List<Narration> }
Narration { readerKey, edition, durationCluster, offers: List<Offer> }     // одна запись на N сайтах
GroupKey  { normTitle: String, authorKeys: SortedSet<PersonKey> }           // §6.1 п.6–7
```

Две хранимые сущности (группа, предложение); озвучки — производное разбиение предложений группы. «Аудиоверсия» как третий уровень Codex §7 не имеет поля в данных сайтов; здесь её заменяют три признака записи: чтец, издание, длительность.

**Алгоритм слияния — детерминированный и независимый от порядка прихода** (нормативно A.3):

1. **Точный ключ.** `GroupKey = (normTitle, authorKeys)`. Равные ключи — одна группа. Предложения без автора — `authorKeys = ∅`, пока свои группы.
2. **Присоединение безавторных.** Группа с `authorKeys = ∅` присоединяется к группе с тем же `normTitle` и непустыми авторами, **только если такая группа ровно одна** (две «1984» разных авторов — безавторная остаётся отдельной; Codex §7: карточка без автора не служит мостом).
3. **Нечёткое слияние** (за флагом до набора корпуса, §11 этап 4). Группы раскладываются по корзинам — одна на каждое слово имени автора длиной ≥ 4 (группа с двумя авторами лежит в нескольких); внутри корзины — лексикографический порядок по `(normTitle, authorKeys)`, попарное сравнение. Пара сливается, если **все** верно: авторы совместимы (для каждого автора одной стороны есть автор другой, чьё множество слов его включает, §6.1 п.7 — `{иванов, петров}` и `{иванов, сидоров}` **не** совместимы); `Dice(bigrams) ≥ 0.92`; множества чисел в названиях равны («том 2» ≠ «том 3»). Слияние — в группу с лексикографически меньшим ключом. Порядок обхода определён данными, не временем прихода, поэтому результат одинаков при любой перестановке ответов (тест B15).
4. **Озвучки.** Внутри группы предложения делятся по `(readerKey, edition)`; внутри — по совместимости длительности: кластеры с разбросом ≤ max(5 мин, 10 %); предложение без длительности присоединяется к кластеру, только если он единственный, иначе образует «длительность неизвестна». Пустой чтец → озвучка «чтец не указан». Так «Пикник на обочине» того же чтеца на 2 ч и 9 ч — две озвучки одной группы (B18), а не одна.
5. **Зеркала.** Предложения одной семьи (`Provider.original()`) внутри одной озвучки — одно предложение с пометкой «+N зеркал»; в счётчике «N сайтов» семья считается одним каталогом.

**Что не склеивается никогда** (согласие с Codex §7): одинаковые названия разных авторов; разные тома; сборник с томом; разные чтецы; известный чтец с неизвестным; записи разной длительности и разного издания — в разные озвучки.

**Представитель группы** (заголовок, обложка, оценка): предложение с максимальным `score`, затем с наибольшим числом заполненных полей, затем из источника с меньшим индексом в порядке пользователя, затем меньший URL. Обложка — его; если `DefaultCover.replaces(photo)` — первая настоящая в группе.

**Лучшее предложение для открытия** — правило про пользователя: (1) запись с прогрессом или скачанная («Продолжить»); (2) из избранного; (3) **не** известное как удалённое или фрагмент и не с сайта, склонного к фрагментам (§6.6); (4) порядок `Sources.active()`, минуя упавшие в этом проходе и «down» по `SourceHealth`; (5) с длительностью и обложкой; (6) меньший URL. Одна озвучка **с одним надёжным сайтом** — тап открывает сразу; иначе — лист «Озвучки и сайты» (§9.5): выбор чтеца и сайта остаётся за слушателем (решение владельца, §14 п. 3).

**Оценка группы** = максимум по предложениям (не сумма: зеркала не накручивают). Уровень — лучший.

**Стабильная идентичность группы** (нужна `DiffUtil` и заморозке §6.5): `Group.id` = URL лексикографически меньшего предложения в момент **первого показа** группы и далее не меняется: при слиянии выживает уже показанный id (если показаны оба — меньший), присоединённая группа исчезает как элемент, выжившая получает payload-обновление; безавторная группа, отделяющаяся при появлении второго автора (редко), появляется новым элементом. Фокус и раскрытие держатся за **URL предложения**, после пересчёта ищется элемент, содержащий этот URL.

**Пагинация и группы.** Группировка не влияет на курсоры источников: «страница без новых групп» не означает конец источника (правило `SearchSession.apply` «страница без новых ключей → конец» остаётся на уровне URL предложений — ответ на F14).

### 6.5. Сортировки и стабильность списка

Меню «Порядок» (иконка ⇅ в строке сводки, PopupMenu с одиночным выбором — тот же язык, что `fillOrderMenu` каталога), по умолчанию **По соответствию**:

| Сортировка | Ключ (по убыванию приоритета) |
|---|---|
| По соответствию | уровень (A→E) · score · родной ранг представителя (`page·1000 + rank`; **только** если профиль сайта `order ∈ {RELEVANCE, UNKNOWN}`, у `DATE`/`VIEWS` ключ — константа) · индекс источника в порядке пользователя · название (ru-коллация) · URL |
| Название А–Я | `normTitle` по `Collator.getInstance(ru)` · автор · URL |
| Автор А–Я | первый автор · название · URL; без автора — в конце |
| Чтец А–Я | группа — по первому по алфавиту чтецу среди озвучек, он показывается первым в строке чтецов · название · URL (меняет смысл сортировки для группы — §14, вопрос 6) |
| Сначала короткие / длинные | по самой короткой / длинной озвучке группы; неизвестные — в конце в обоих направлениях |
| Порядок сайта | только во вкладке сайта: как отдал сайт (умолчание вкладки) |

Компаратор транзитивный, без нечётких сравнений (все пороги применяются на этапе группировки). Сортировка действует на загруженное; подпись «отсортировано загруженное», когда у источников есть ещё страницы. Сортировка и группировка — настройки (вкус); вкладка сбрасывается на «Все» при новом запросе.

**Стабильность списка** (ответ на W18): приходы объединяются и применяются не чаще раза в 400 мс через `AsyncListDiffer` по `Group.id` / `offer.url` (diff — не на главном потоке, списки до 1500). Пока пользователь не касался списка — вставки идут сразу, список растёт по релевантности. После первого действия (скролл, тап, фокус D-pad в списке) элементы от нулевого до последнего видимого **замораживаются**: новые вставляются только ниже, а те, что по рангу попали бы выше, считаются в плашку «↑ Новых выше: N» (тап — пересортировать и прокрутить к началу). Слияния групп выше якоря тоже откладываются до «Новых выше». Новый сайт у видимой группы обновляет «N сайтов» на месте через payload. Явная смена сортировки или области перестраивает список сразу с сохранением якоря. Политика Codex §11, с ней согласны.

**Представления списка** (решение владельца, §14 п. 6 — гибкость). Переключатель в меню «Порядок» (и в ⋮): **Произведения** (группы, по умолчанию), **Озвучки** (плоский список записей: «название · чтец · длительность · N сайтов», без обёртки в группу), **Карточки** (плоский список предложений, как сегодня, с названием сайта). Представление запоминается в настройках и в снимке; все три работают на одном и том же наборе предложений, без запросов. Сортировки по представлениям:

| Представление | Сортировки |
|---|---|
| Произведения | по соответствию · название · автор · чтец (первый чтец группы) · сначала короткие / длинные (по озвучкам группы) |
| Озвучки | по соответствию · название · автор · **чтец** (естественная для записей) · длительность · число сайтов |
| Карточки | по соответствию · название · автор · чтец · длительность · **источник** (порядок пользователя, внутри — порядок сайта) |

Вкладка сайта всегда показывает «Карточки» этого сайта с умолчанием «Порядок сайта».

**Пагинация и «Все».** После появления ранжирования (этап 3) бесконечная прокрутка во «Все» **выключается**: вторые страницы 13 сайтов, вставленные по релевантности, сдвигают список. Вместо неё — подвал «Искать дальше · ещё страницы на 8 сайтах» (один тап → следующая страница каждого источника с продолжением, через «Новых выше»). Во вкладке сайта — бесконечная прокрутка **только этого сайта** (`SearchSession.loadNext(source)`), «до заполнения» — не больше двух страниц за раз. До этапа 3 автоподгрузка остаётся как есть (выключать её без ранжирования — регрессия).

### 6.6. Надёжность предложения: фрагменты и удалённые книги

Владелец указал на две вещи, которые знает каждый слушатель этих сайтов: **часть сайтов показывает книгу, но даёт только ознакомительный фрагмент LitRes**, и **часть сайтов показывает карточку книги, которой уже нет** (удалена правообладателем). Сегодня это выясняется только при открытии: `tracks()` адаптера бросает `BookRemovedException` (есть у Aknigi24, Аудиокнига Life, Audiokniga.one, Audiokniga-online, Аудиокниги.fun, Audioknigi.pro, Библус, Bookish, `AudioModel`), и `BookPresenter` показывает тост «Удалена правообладателем. Поищите на другом источнике». Поиск об этом ничего не знает и предлагает такие карточки наравне с полными. Исправление — три источника знания и одно хранилище:

1. **Признаки на карточке, без запросов.** URL в разделе `/paid/` (Akniga, Audiokniga.one — книги, продаваемые через LitRes); значок LitRes или пометка «Фрагмент» в карточке (Книга в ухе, ИзиБук, Akniga уже **отбрасывают** такие карточки в листингах — это поведение сохраняется); длительность предложения меньше 25 % максимальной длительности в его озвучке → «вероятно фрагмент». Результат — поле `Offer.availability ∈ {FULL, PREVIEW_LIKELY, UNKNOWN}` на этапе пост-обработки.
2. **Склонность сайта.** Флаг профиля `previewProne` (§7.1) у сайтов, где у многих популярных книг только фрагмент LitRes: Golosknig, Audioknigi.pro, Bookish, Audiokniga.one (наблюдение `tasks/plan.md` §12.13). Он понижает сайт в правиле «лучшее предложение» и даёт подпись «часто фрагмент» в листе; карточки не скрывает.
3. **Память о проверенных книгах** — `AvailabilityMemory`: `URL → {FULL | PREVIEW | REMOVED, когда}` в небольшом файле `filesDir/search/availability.json` (LRU 2000, TTL 30 дней). Пишут: `BookPresenter` при `BookRemovedException` и при успешном старте воспроизведения (FULL); проверка из листа (п. 4). Читает поиск: предложение с REMOVED/PREVIEW помечается в карточке и листе («удалена · проверено 3 дня назад»), в «лучшем предложении» пропускается; группа, у которой **все** предложения REMOVED, остаётся в списке с пометкой — пользователь должен видеть, что книга была, а не гадать.
4. **Проверка из листа** (§9.5) — на открытие листа «Озвучки и сайты» для его предложений без свежей записи в памяти (не больше 6, параллельно ≤ 3, таймаут 8 с, через `parser.fetch(bookUrl)`) вызывается новый метод адаптера `availability(Document page, String bookUrl) → FULL | PREVIEW | REMOVED | UNKNOWN`, выделенный из уже существующих проверок внутри `tracks()` (селекторы `.litres-player`, `a.full-litres`, `iframe[src*=litres.ru]`, текст «Ознакомительный фрагмент», `BookRemovedException.isNotice`); `tracks()` продолжает ими пользоваться. Строки листа показывают спиннер, затем ✓ / ◔ / ✕. Это единственное место, где поиск делает запросы к страницам книг, и оно всегда — по действию пользователя (открыл лист), не N+1 на выдачу.

Статусы в интерфейсе: ✓ «полная» (FULL из памяти или по длительности), ◔ «фрагмент» (PREVIEW / PREVIEW_LIKELY / `previewProne` без проверки — подпись различается: «фрагмент», «вероятно фрагмент», «часто фрагмент»), ✕ «удалена», «?» не проверено. Карточка группы: «5 сайтов · 1 фрагмент · 1 удалена». Избранное и история не затрагиваются: память о доступности — подсказка, не фильтр.

## 7. Стратегия по источникам: профили, план запроса, зеркала, время

### 7.1. Профиль поиска в `SourceParser`

Одна декларация на адаптер, значения по умолчанию соответствуют сегодняшнему поведению:

```java
/** Что известно о поиске сайта; данные, не код. По умолчанию — «не известно», как сегодня. */
default SearchProfile searchProfile() { return SearchProfile.UNKNOWN; }

final class SearchProfile {
  enum Scope { TITLE_ONLY, TITLE_AUTHOR, TITLE_AUTHOR_SERIES, TITLE_AUTHOR_READER, FULLTEXT, UNKNOWN }
  enum Order { RELEVANCE, DATE, VIEWS, UNKNOWN }        // порядок выдачи сервера
  Scope   scope;              // что индексирует серверный поиск (по endpoint книжного поиска, не other-source)
  boolean peopleAuthors, peopleReaders;                 // = searchUrl(AUTHORS|PERFORMERS) != null
  int     minQueryChars;      // 0 = нет ограничения; DLE-сайты с проверенным сообщением: 4
  boolean caseSensitive;      // true = повтор в другом регистре нужен (сегодняшнее поведение); false — после замера
  int     requestsPerSearch;  // последовательных HTTP-запросов в одной операции поиска книг (Lis10book 2, Akniga люди 2)
  int     pageSize;           // 0 = неизвестно
  int     expectedMs;         // типичное время; > 5000 → чип «долго отвечает» с начала
  int     minIntervalMs;      // пауза между запросами к хосту (Aknigi24: 1000)
  Order   order;
  boolean sharedWithChips;    // одна страница даёт и книги, и авторов/циклы (Книга в ухе, ABMP3)
  boolean ownFallback;        // адаптер сам делает резервный шаг внутри fetch (Lis10book) — внешний не нужен
  String  titleOnlyParam;     // путь «только название» (Audiokniga-online: full_search=1&titleonly=3), null = нет
  boolean previewProne;       // у многих популярных книг только фрагмент LitRes (§6.6): Golosknig, Audioknigi.pro, Bookish, Audiokniga.one
}
```

Профиль — данные: сверяется тестами (у сайта с `peopleAuthors` `searchUrl(AUTHORS, …) != null`; `requestsPerSearch` ≥ 1) и заполняется измерением (§7.7).

### 7.3. План запроса и единственный резервный шаг

Планировщик (`search/SearchPlanner`, чистая функция `plan(request, sources, profiles) → List<Step>`) строит для источника **один основной шаг** и **не более одного автоматического резервного** за проход. Дальше — только по действию пользователя («Искать дальше», повтор по чипу).

| Ситуация | Основной шаг | Резервный шаг |
|---|---|---|
| `len(text) < minQueryChars` | не слать; SKIPPED «короткий запрос для этого сайта» | — |
| Название, сайт с `titleOnlyParam` | путь «только название» | — |
| Автор / Чтец, сайт с поиском людей | книжный поиск + поиск людей (параллельно, в общем бюджете) | — |
| любая, иначе | книжный поиск с полным текстом | по приоритету ниже, один на источник |

**Приоритет резервных шагов** (первый применимый, остальные не делаются):

1. **429 с `Retry-After`** ≤ остатка бюджета операции → один повтор после паузы через лимитер хоста (W36).
2. **Подсказка от соседей** — для `scope = TITLE_ONLY` без `ownFallback` (ABMP3; База Книг и Audioboo — после того как замер переведёт их «?» в `TITLE_ONLY`), запрос из ≥ 2 значимых слов, **только область «Везде»** (в области «Название» все слова и так считаются названием, подсказка не имеет смысла), ответ EMPTY. **Момент решения фиксирован**: конец первого прохода (все не пропущенные ответили) или мягкий предел 20 с — что раньше. Консенсус считается по **источникам**: голос источника — распределение слов запроса по полям у его лучшего предложения; семья зеркал — один голос. Нужны ≥ 2 независимых источника с одним и тем же набором слов в полях «автор»/«чтец» и ≥ ⅔ голосовавших за него (на «булгаков собачье сердце» все ответившие сайты дают одно произведение и один набор `{булгаков}` — этого достаточно; три разных произведения не требуются). Тогда сайту уходит запрос из слов, назначенных названию; его карточки проверяются исходным запросом локально (слова-авторы должны совпасть с полем автора), иначе отбрасываются. Один запрос на источник за проход. Для `FULLTEXT`-сайта с `titleOnlyParam` (Audiokniga-online) при том же консенсусе резерв — путь `titleonly` со словами названия. Честное ограничение: набор запросов зависит от того, какие ответы пришли к моменту решения, но ограничен одним запросом на источник.
3. **Другой регистр** — только у сайтов с `caseSensitive = true` (до замера — у всех, как сегодня), сразу после ответа этого сайта, не после барьера.

Переход на зеркало при сбое (§7.4) — не резервный шаг источника, а другой источник; он не расходует этот лимит.

Что **не делается автоматически**: перебор перестановок, поиск каждым словом, «одно редкое слово», обход каталога автора через индекс (согласие с Codex §14).

### 7.4. Зеркала

Две семьи по данным `Provider`: **Книгоблуд (оригинал) — Библус — Голосом** и **Akniga (оригинал) — Golosknig**. Факты инвентаризации: у членов семьи **разные пути поиска, размеры страниц, полнота карточек и ширина индекса** (Книгоблуд отдаёт первого автора и чтеца и не ищет по чтецу, Голосом — всех и ищет по чтецу; Golosknig не отдаёт цикл и жанр). Поэтому «одинаковые id» и «подстановка домена» — не предположение, на которое можно опереться, а пустой ответ одного члена **не доказывает** отсутствия книги в семье.

Политика:

1. **По умолчанию — как сегодня**: все включённые члены семьи опрашиваются параллельно; дубли схлопываются в одно предложение «+N зеркал» (§6.4 п.5), «N сайтов» считает каталоги. Это снимает W19 без риска потери выдачи.
2. **Настройка «Зеркала: один запрос на семью»** (выключена). Включённая: предпочтительный член — с самым широким профилем `scope` для текущей области (в области «Чтец» — Голосом), при равенстве — выше в порядке пользователя, затем лучше по `SourceHealth`. Его OK → остальные не опрашиваются, чипы «через Голосом», тап — поиск именно там. Его **EMPTY → следующий член с более широким индексом опрашивается**, иначе — тоже EMPTY семьи с чипами «через …». TIMEOUT / ERROR / BLOCKED → следующий активный член с первой страницы в остатке бюджета прохода (курсоры не переносятся); следующие страницы — тому, кто дал первую.
3. Переводить настройку в умолчание — только после замера совпадения выдач членов семьи на корпусе (§7.7). Доказательство эквивалентности каталогов — отдельный замер, его состав: разные авторы, чтецы, дальние страницы, пустые запросы.

Карточки сохраняют URL сайта, с которого пришли: избранное, история и загрузки не знают о семьях.

### 7.5. Общие ответы и кеш внутри прохода

- **Книга в ухе**: страница поиска содержит `#search_blocks` с авторами и циклами (`SearchebleModel.getSearcheblPOJO` грузит её второй раз). `Knigavuhe.searchExtras(Document)` возвращает чипы из того же `Document`; второй запрос уходит. Ссылка «все результаты» грузится лениво по нажатию «ещё авторы».
- **ABMP3**: один статический ответ содержит все книги и блок авторов; сегодня он грузится 2 раза на поиск и ещё по разу на каждую «страницу» по 40, причём `Abmp3.searchUrl` добавляет `&page=N`, который сервер игнорирует. Адаптер отдаёт **один и тот же URL для любой страницы** (логическая страница остаётся аргументом `searchResults(page, pageNo)`, который уже нарезает по 40), и кеш ответов (§8.4) по этому URL делает страницы 2… и `AutorsSearchABMP3.parse` (остаётся — его вызывает `Abmp3.searchPeople`) чтением одного документа.
- **Поиск людей** для строк «Авторы»/«Чтецы» — те же `searchUrl(AUTHORS|PERFORMERS)`, что у экрана «Авторы»/«Чтецы»; ответ кешируется и переиспользуется, если пользователь затем откроет тот экран.

Экономия у нового пользователя (13 сайтов, область «Везде»): 15 запросов → 13 (без двух повторных загрузок) и минус k повторов регистра у сайтов, где замер покажет `caseSensitive = false`. У пользователя с включёнными семьями и настройкой «один запрос на семью» — ещё −3. Приёмка этапа 5 формулируется как «число книжных запросов за проход = число источников, без дублей», не как фиксированное «≤ 10».

### 7.6. Время: три лимита, прогресс, параллелизм

**Лимит HTTP-попытки** — как сегодня: `timeoutMs()` сайта (10 с; 25/30/40 у медленных). Не трогаем.

**Лимит операции источника** — из профиля: `timeoutMs × requestsPerSearch + паузы лимитера + 5 с` → один GET: 15 с; Lis10book (основной + подсказки): 25 с; поиск людей Akniga (ключ + POST): 25 с; Aknigi24 с лимитером: 15 с + паузы; медленные сайты: 30 / 35 / 45 с. До этапа 6 остаётся сегодняшнее `max(20, requestSeconds())`. Лимит ведётся на `Schedulers.computation()` и монотонных часах (как в `SourceProbe`).

**Предел прохода** — абсолютный: **60 с** от отправки, включая резервные шаги и зеркала; что не ответило — `STOPPED` (не ошибка, повтор по чипу). Это даёт утверждению «дальше ждать нечего» точный смысл. Поведение интерфейса внутри предела:

| Момент от старта | Что показывает экран |
|---|---|
| 0–2 с | индикатор под чипами, чипы «ищет» |
| 2 с | сводка «Ответили 5 из 13 · найдено 31», обновляется по каждому ответу |
| с начала | сайты с `expectedMs > 5000` — ⏱ «долго отвечает» сразу |
| 8 с | остальные не ответившие — ⏱ «долго отвечает» |
| 20 с | кнопка «Остановить ожидание» (мягкий предел; момент решения для подсказки от соседей) |
| 60 с | абсолютный предел: оставшиеся → STOPPED, «Все» жёлтый |

Ни одна операция не прерывается раньше своего лимита без действия пользователя, кроме абсолютного предела 60 с (операции с лимитом 45 с и резервный шаг после них могут в него упереться — тогда STOPPED с повтором по чипу): медленный сайт, ответивший на 28-й секунде, добавляет карточки через «Новых выше». Бюджет внешнего резервного шага — отдельная операция с собственным лимитом из профиля, внутри тех же 60 с.

**Параллелизм.** Три ограничителя, без шести приоритетов: (а) **один запрос на источник одновременно** внутри сессии (сегодняшний `MAX_PARALLEL` по смыслу); (б) **один запрос на хост** во всём приложении, у Aknigi24 — плюс пауза 1 с (`minIntervalMs`); (в) **общий семафор 16** на все запросы поиска и проверки сайтов, с одним правилом очереди: первые страницы книжного поиска видимого прохода идут раньше поиска людей, резервных шагов, следующих страниц и `SourceHealth` (который откладывается, пока идёт поиск). Снижать веер до 4–6 без измерения не надо: при слотах = сайтам время прохода равно самому долгому сайту; при 4 слотах очередь складывает задержки, и Bookish на 40 с задержит ещё троих. Но и утверждать «13 оптимально» без замера нельзя — 4/6/8/13 измеряются на этапе 7 как предлагал Codex §9. Слот семафора освобождается по **факту** остановки транспорта, а не по отписке Rx, иначе лимит фиктивен (до T09 это означает: освобождение по HTTP-таймауту).

**Отмена.** До T09 отмена логическая: подписка снята, поток `io` занят до HTTP-таймаута. С T09 — `OkHttpClient` за Jsoup-парсером, `Call.cancel()` по отписке, deadline в запросе; `SiteHttp` сохраняет правила прокси, TLS, cookies, POST-страниц, классификации challenge — меняется только исполнитель запроса.

**Реакции на ошибки** — таблица Codex §9 принимается с двумя уточнениями: единый счётчик физических попыток на операцию (внутренние повторы 429 Aknigi24 заменяет лимитер хоста), и для этого `ProviderPage` получает `httpStatus` и `retryAfterSeconds`, а статус `RATE_LIMITED` отделяется от `BLOCKED` (W36): на чипе — «подождите 30 с», а не «нужны cookies».

### 7.7. Что измерить, прежде чем настраивать

Расширить `LiveDumpTest` (уже есть `TIMED`-запросы «Чужой» и «маг поневоле») до восьми запросов на сайт — одно слово, два слова, автор + название, автор, чтец, цикл, нижний регистр, опечатка — и писать `search-times.txt` **и** `search-profile.txt`: время, число карточек, совпадение множеств URL для «Кинг»/«кинг» (регистрозависимость), доля карточек с автором/чтецом/длительностью, порядок (релевантность или дата), для семей зеркал — совпадение множеств названий. Один запуск на машине владельца с паузами 2 с между запросами одного хоста (Aknigi24 — 5 с) — около 25 минут. Это **этап 2.5** плана (§11), до профилей: без него `caseSensitive = true` у всех, `expectedMs` — по комментариям в коде, `scope` — по таблице §7.2 с «?».

### 7.8. Здоровье источника и порядок старта

`SourceHealth` (первая страница каталога раз в сутки) используется для порядка старта при нехватке слотов и выбора зеркала при включённой настройке. Отдельной статистики поиска по сайту не вводим (Codex §8 предлагал «недавнюю успешность поиска»): ещё одно хранилище ради выбора зеркала не окупается, пока политика семей — настройка. Больной сайт всё равно опрашивается — пользователь видит результат на чипе.

## 8. Кеш и восстановление последнего поиска

### 8.1. Два уровня

| Уровень | Что | Где живёт | Срок |
|---|---|---|---|
| Снимок последнего поиска | запрос, область, предложения с источником/страницей/позицией, состояния и курсоры источников, найденные люди и циклы, сортировка, вкладка, якорь | **память процесса** (синглтон; покрывает самый частый случай W21: чип автора → `finish()` → снова «Поиск») **и** файл `filesDir/search/last.json` через `androidx.core.util.AtomicFile`, Gson (уже в проекте) | память — жизнь процесса; файл — 3 дня, возраст всегда подписан; старше 3 дней — восстанавливается только запрос |
| Кеш ответов | разобранный ответ (`Document` / `JsonPage`) по **URL** | память процесса, LRU 50 | 10 мин; пустой ответ — 2 мин; ошибки и 429 — не кешируются |

История запросов: `SearchRecentSuggestions` остаётся как есть (переключение на `DATABASE_MODE_2LINES` пересоздало бы таблицу и стёрло историю); область последних 50 запросов хранится в том же `search/` файле `history.json` и подставляется при выборе подсказки. Room-таблиц для поиска не нужно.

### 8.2. Состав снимка

```
{ schema: 1, savedAt, appVersion, complete: true|false,            // false = остановлен пользователем / прерван
  request: { text, scope: ["AUTHOR"] },
  sources: [ { id: "knigoblud", execution: "DONE", result: "OK", count: 12, millis: 1840,
               pagesLoaded: 2, nextPage: 3, hasMore: true, effectiveUrl: "…", viaMirror: null,
               savedAt: 1730470800000, message: null }, … ],
  offers:  [ { source: "akniga", page: 1, rank: 0, book: { …BookPOJO… } }, … ],
  people:  { authors: [ {name, url, source} ], readers: [...], series: [...] },
  ui:      { sort: "RELEVANCE", tab: "ALL", grouping: true, anchorUrl: "https://…", anchorOffset: 120 },
  truncated: false }
```

Не сохраняется: DOM, обложки, cookies, оценки и группы (пересчитываются из `offers` за миллисекунды — снимок не зависит от версии ранжирования).

**Пределы и усечение.** ≤ 1500 предложений и ≤ 2 МиБ. При превышении удаляются **целые последние страницы** источников (по кругу, начиная с источника с наибольшим числом страниц), у такого источника `nextPage` сбрасывается на первую удалённую страницу, `hasMore = true`, `truncated = true`, сводка после восстановления: «сохранено не всё · Искать дальше». Так продолжение никогда не оставляет дырок (Codex §10 разбирал именно это).

**Запись**: по завершении прохода, при остановке, при `detachView` презентера (уход с экрана), и не чаще раза в секунду во время прихода результатов. Вне главного потока, одним писателем. Новый запрос **не стирает** снимок предыдущего до своего первого непустого ответа (или корректного пустого завершения).

### 8.3. События и поведение — одна таблица

| Событие | Поведение |
|---|---|
| Открыт экран без запроса (кнопка лупы) | снимок показан сразу: текст в поле выделен целиком (первая буква заменяет его), клавиатура на телефоне не открывается сама, «Все» со значком часов, сводка «Результаты от 14:20 · Обновить»; ноль запросов |
| Тот же запрос и область, проход **идёт** | игнорируется |
| Тот же запрос и область, снимок **моложе 10 мин** | показан снимок, прокрутка к началу, ноль запросов; «Обновить» — явно (кнопка, свайп вниз) |
| Тот же запрос и область, снимок **старше 10 мин** | снимок показан и запускается обновление: источник со статусом «обновляется», его старые предложения остаются до его ответа и **заменяются** ответом целиком (все страницы); упавший при обновлении источник сохраняет старые предложения с подписью «данные от 14:20» (`sources[i].savedAt`) |
| Другой запрос | обычный поиск; снимок заменится после первого непустого ответа |
| Тот же запрос, другая область | локальный пересчёт (§5.3); запросы только за новым путём (поиск людей; обычный книжный путь для сайта, искавшего «только название») |
| Показ снимка или секции «В библиотеке» | если родительский контроль когда-либо начнёт фильтровать выдачу поиска (сегодня он проверяет книгу при открытии, `BookActivity`), фильтр применяется к восстановленным карточкам перед показом |
| Поворот | ничего не делается — Moxy держит презентер и состояние |
| Смерть процесса → возврат | презентер новый; читается снимок (память пуста → файл): вкладка, область, сортировка, якорь; `RUNNING/QUEUED` → «прервано», повтор по чипу; если снимка нет — запрос из `savedInstanceState` подставляется в поле без автозапуска |
| `finish()` после чипа автора (W21) и повторное открытие поиска | снимок из памяти, мгновенно |
| Нет сети | снимок с плашкой «Нет сети · показан сохранённый поиск», запросы не делаются |
| «Очистить историю поиска» | удаляет и снимок, и `history.json` |

### 8.4. Кеш ответов и «ноль HTTP»

Ключ — **фактический URL запроса** (в нём уже есть сайт, категория, эффективный запрос, путь `titleonly`, страница); сортировка, область и вкладка в ключ не входят — они локальны. Кеш делает бесплатными: смену вкладки и сортировки, группировку/разгруппировку, возврат из книги, повторный submit в течение 10 мин, страницы 2… ABMP3, блок авторов ABMP3 и чипы Книги в ухе. «Обновить» очищает записи этого запроса и запускает проход заново.

### 9.2. Чипы источников: состояния и цвета

Порядок чипов: «Все», затем `Sources.active()` в порядке пользователя с включённым `prefKey`; **порядок никогда не меняется** от статуса. Material `Chip` стиля Choice, 32 dp, на телефоне `ensureMinTouchTargetSize` 48 dp, `focusable` явно (W25). **Выбор** (вкладка) — обводка 2 dp `?attr/hrefColor` и жирный текст, `checked` для TalkBack; заливка `filter_selected.xml` **не используется** (конфликт с цветом статуса). **Статус** — `chipIcon` + слабая заливка 16 % цветом статуса + число. Текст всегда `?attr/colorPrimaryText` — во всех трёх темах. Цвета в `colors.xml`: `source_up` #4CAF50 и `source_down` #E53935 (сегодня константы `SourcesDialogFragment`), новый `source_partial` #FFB300.

| Состояние | Иконка · текст | Заливка | contentDescription |
|---|---|---|---|
| в очереди / ищет | статичные песочные часы · «Akniga» | нет | «Akniga: ищет» |
| найдено | ✓ зелёный · «Akniga 12», «12+» если есть ещё страницы | зелёная 16 % | «Akniga: найдено 12, есть ещё» |

| пропущен | «–» серый · «Голосом» | нет | «Голосом: через Книгоблуд» / «…запрос короче 4 символов» / «…по карточкам» |

Это отображение `SourceState` (§10.1): `execution × result × флаги`; «долго отвечает» — производное (RUNNING дольше 8 с или `expectedMs > 5000`). Есть книги, но упала **следующая** страница → чип остаётся зелёным с маленьким ⚠ и подписью «страница 3 не загрузилась». Знаменатель «ответили N из M» — запланированные источники без SKIPPED.

**Почему пустой ответ серый, а не светло-зелёный** (владелец просил «успешно → светло-зелёный»): зелёный должен означать «здесь есть что слушать», тогда глаз за полсекунды находит полезные сайты; «успешно, но ноль» — серый «0». Если владелец предпочитает зелёный для любого успеха — это одна константа (§14).

**Почему нет мигания и смены цвета в процессе** (владелец просил «эффект меняющего цвета и мигания»): 13 мигающих элементов в течение 20–60 секунд тратят батарею, отвлекают, мешают TalkBack и нарушают рекомендации доступности о вспышках; «ищет» читается по песочным часам, а живость процесса дают индикатор под чипами и счётчик в сводке, меняющиеся при каждом ответе. Если движение всё же нужно — один общий `ValueAnimator` плавно пульсирует **иконку** часов (alpha 0.5↔1.0, 1.2 с) у всех ищущих чипов, выключается на TV и при `ANIMATOR_DURATION_SCALE == 0`; это отдельное решение владельца (§14), в план не входит.

На TV — удержание центральной кнопки, и обязательно видимый дубль в пустом состоянии вкладки («Повторить Библус»). ### 9.3. Список: строки сверху вниз

1. **«В вашей библиотеке»** — до 3 совпадений из избранного и истории прослушивания (`FavoriteDao`/`HistoryDao`, та же оценка §6.2 по полям записи), **мгновенно, до сети и без сети**, с подписью «Продолжить · 45 %».
2. **«Авторы» / «Чтецы» / «Циклы»** — **переносимая** `ChipGroup` (две строки, затем «ещё N»), не горизонтальный скроллер внутри списка (ловушка фокуса, §13); сущности из поиска людей и блоков циклов, дубли сняты по множеству слов имени (§6.1 п.7); тап — как сегодня `returnResult` (§10.5), выдача возвращается из снимка в памяти (W21). Строка уезжает при прокрутке, никакого прятания по скроллу.
3. **Произведения** — во «Все» группы (§9.4), во вкладке сайта — обычные карточки с прогрессом и «скачано» (W23).
4. **«Без данных о чтеце (N)»** / «…о цикле» — свёрнутая секция в областях «Чтец»/«Цикл».
5. **«Похожие (N)»** — свёрнутая секция уровня E, когда есть хоть одно A–D.
6. **Подвал**: «Искать дальше · ещё страницы на 8 сайтах» (только во «Все», с этапа 3); «Скрыто областью «Автор»: 23 · Показать все»; «Сохранено не всё»; «Это всё, что отдали сайты».

### 9.4. Карточка группы (во «Все»)

Основа — `books_recycler_item.xml` и `_big` (по настройке) той же высоты, чтобы сетка 2–4 колонки и TV не ломались; группа связана с представительным `BookPOJO` и счётчиками.

- обложка и название — представителя (§6.4); автор — `?attr/hrefColor`;
- справа вверху вместо названия сайта — **«5 сайтов»** (каталоги: семья зеркал — один), с уточнением «· 1 фрагмент · 1 удалена», когда это известно (§6.6);
- строка чтецов в поле `artist`: «Клюквин, Князев +1» — первым тот, что отвечает сортировке/лучшему предложению;
- снизу «⏱ 8 ч 40 мин – 9 ч 05 мин · 3 озвучки»;
- кольцо прогресса и «скачано» — если есть у **любой** записи группы;
- причина совпадения — только если совпало **не название**: «Совпал чтец: Князев»;
- число оценки не показывается (§6.2); в долгом нажатии — «Почему здесь: название 100, автор ✓»; переключатель в настройках для числа на карточке.

**Тап**: одна озвучка → лучшее предложение (§6.4); несколько → лист «Озвучки и сайты». **Долгое нажатие**: существующее меню книги (`bootom_sheet_books_menu`) для лучшего предложения плюс «Открыть на другом сайте»; «В избранное» добавляет лучшее предложение (избранное хранит URL).

Вкладка сайта: плоский список, сортировка по умолчанию «Порядок сайта».

### 9.5. Лист «Озвучки и сайты»

`BottomSheetDialogFragment` с аргументом `groupId` (не `BottomSheetDialog`, построенный в презентере, как сегодняшнее меню: диалог должен пережить поворот и держать фокус D-pad), данные — из `SearchUiState` по id:

- заголовок: обложка, название, автор группы;
- строка озвучки: «Князев Игорь · 9 ч 05 мин · 3 сайта (1 фрагмент)»; тап — лучшее **надёжное** предложение озвучки (§6.4);
- справа «Сайты (3)» — отдельная цель фокуса (TV — D-pad вправо), раскрывает сайты озвучки, каждый со статусом доступности (§6.6): «Akniga ✓ · слушаете 45 %», «Книга в ухе ? · проверяется…», «Bookish ◔ часто фрагмент», «Audiokniga.one ✕ удалена · проверено 3 дня назад», «Библус · сейчас не отвечает» (статус прохода, иначе `SourceHealth.last`); тап — открыть именно там, даже если помечен (пользователь решает сам);
- при открытии листа запускается проверка доступности непроверенных предложений (≤ 6, параллельно ≤ 3, 8 с), строки обновляются по мере ответов; результат остаётся в памяти о доступности;
- порядок сайтов в раскрытии: полные → непроверенные → «часто фрагмент» → фрагмент → удалённые; внутри — порядок пользователя;
- лучшая строка первая и в фокусе: на TV открыть книгу — два нажатия центра;
- внизу «Показать все карточки» — разгруппировать эту группу в списке.

### 10.2. Контракт `SearchSession.Listener` (новый)

```java
interface Listener<T> {
  void onSourceState(SourceState state);                       // при каждом изменении любого источника
  void onPage(Source<T> source, int page, List<T> items);       // новые предложения источника
  void onReplace(Source<T> source);                            // при обновлении: его прежние предложения снять (пришла свежая страница 1)
  void onPassFinished(boolean complete);                       // false = остановлено пользователем или предел 60 с
}
// плюс: void restore(SearchSnapshot s) — поднять курсоры, состояния (RUNNING → STOPPED «прервано») и предложения без запросов
```

Закреплённые тестами свойства (сохранить все 13 сегодняшних + новые): поздний ответ прежнего поколения игнорируется; `loadNext(source)` не ждёт других; `retry(source)` повторяет только его страницу; `SKIPPED` не стартует и не получает таймаут; зеркало стартует только после сбоя предпочтительного (при включённой настройке); `RUNNING` публикуется при старте; ограничители §7.6 не превышаются при книгах + людях + резервных шагах; `stop()` переводит RUNNING → STOPPED и ничего не оставляет в `pending`; `refresh()` вызывает `onReplace` только после непустой свежей первой страницы или корректного пустого завершения источника.

### 10.4. Инварианты (проверяются тестами)

1. Поздний ответ, оценка или запись кеша старого поколения не заменяет новые.
2. У каждого источника свой курсор и состояние; `retry` касается только его.
3. Сортировка, смена вкладки, смена области без нового пути, разгруппировка, возврат из книги — **ноль HTTP**.
4. Не стартовавший источник не получает ни таймаут, ни успех.
5. Группировка и сортировка не меняют множество предложений; результат группировки одинаков при любой перестановке входа; id показанной группы не меняется при слиянии.
6. Полнота прохода (`complete`), свежесть (`savedAt` по источнику) и результат последнего запроса хранятся раздельно.
7. URL книги, прогресс, избранное и загрузки не зависят от группировки.

### 10.5. Режимы экрана и навигация

- **`MODEL_AUTOR` / `MODEL_ARTIST`** (поиск людей одного источника с возвратом результата). До этапа 5 — поведение сохраняется: тот же презентер, та же `SearchSession<GenrePOJO>`, новый экран показывает плоский список строк `person` без чипов источников и без группировки; `returnResult` остаётся. На этапе 5 эти режимы **поглощаются** областью: вызовы из каталога открывают поиск с областью «Автор»/«Чтец», выбранной вкладкой текущего источника и теми же сущностями в строке «Авторы»/«Чтецы»; тап по сущности возвращает результат, как сегодня. Старые константы остаются для совместимости вызовов.
- **`returnResult` + `finish()`** (чипы авторов/циклов, пункты долгого нажатия). Страница автора — это `BooksFragment` внутри `MainActivity`, своей Activity у неё нет, поэтому «открыть поверх поиска» без хост-Activity невозможно. Решение этапа 2: механизм не меняется, а потеря выдачи (W21) закрывается снимком в памяти — повторное открытие поиска мгновенно показывает прежние результаты. Отдельная хост-Activity для `BooksFragment` — идея на потом.
- **Голос** (`MediaPlayerService.onPlayFromSearch`): область «Везде», вкладка «Все», сортировка по соответствию; при точном совпадении с книгой из библиотеки — позже «сразу играть».

## Приложение A. Алгоритмы

Нормативный псевдокод; таблицы §6 — пересказ.

### A.1. Нормализация, имена, издание

```
key(s):
  s = NFC(s).toLowerCase(ROOT).replace('ё','е')
  s = foldLatinLookalikes(s)                 // a c e o p x y → а с е о р х у в словах с кириллицей
  s = replaceAll("[\\p{P}\\p{S}]+", " ")      // любая пунктуация и символы Unicode → пробел
  s = replaceAll("(?U)\\s+", " ").trim()     // UNICODE_CHARACTER_CLASS: NBSP и прочие пробельные
tokens(s)  = key(s).split(" ")               // пустые отбрасываются
STOP       = {и, в, на, с, о, а, у, к, по, из, за, не, от, для, the, of, a, and}
significant(tokens) = [t : isNumber(t) or (len(t) ≥ 2 and t ∉ STOP)]; если пусто → tokens   // числа значимы всегда
EDITION_MARKERS = {полная версия, полный вариант, сокращ, спектакль, радиоспектакль, радиопостановка,
                   аудиоспектакль, инсценировка, фрагмент, отрывок, с музыкой}
splitEdition(title):
  edition = ""
  for каждая скобочная группа в title:        // «(том 1)», «(сборник)» остаются в названии
    if она содержит маркер из EDITION_MARKERS → edition += группа; группа удаляется из title
  marker = первый маркер из EDITION_MARKERS вне скобок → edition += marker, удаляется из title
  return (key(title), key(edition))          // числа, «том N», подзаголовки остаются в title
persons(field):                               // "А, Б и др." → люди
  parts = split(field, /\s*(,|;|/|&|\s и\s)\s*/) без «др», «и др»
  return [personKey(p) for p in parts if personKey(p) non-empty]
personKey(name):
  words = tokens(name)
  words = [w : len(w) > 2 and not patronymic(w)]      // инициалы и отчества вон
  initials = [w : len(w) ≤ 2]
  if contains hyphen-joined form → add joined form as extra word (салтыковщедрин)
  return PersonKey(sortedSet(words), initials)
patronymic(w) = w endsWith one of {ович, евич, ьич, ич, овна, евна, ична, ьевна} and len(w) ≥ 6
samePerson(a, b):                             // для нечёткого шага и дедупа сущностей
  if a.words empty or b.words empty → compare initials only (равные множества)
  small, big = by |words|
  return small.words ⊆ big.words               // инициалы в сравнение не входят: «М. А. Булгаков» = «Булгаков» (B24)
authorsCompatible(groupA, groupB):            // авторы группы = объединение авторов её предложений
  small, big = by |authors|
  return ∀ p ∈ small.authors: ∃ q ∈ big.authors: samePerson(p, q)   // лишний соавтор у одной стороны допустим
                                               // (сайты опускают соавторов); {иванов, петров} vs {иванов, сидоров} — нет
bigrams(s) = множество пар соседних символов key(s) без пробелов
dice(A, B) = 2·|A∩B| / (|A|+|B|)
```

### A.2. Оценка (`SearchMatcher.score`)

```
score(offer, req):
  Q   = tokens(req.text); if Q empty → (E, 0)
  SIG = significant(Q)
  fields = req.scope ∅ ? {TITLE:1.0, AUTHOR:0.95, SERIES:0.9, READER:0.9} : {f:1.0 for f in scope}
  // рёбра: (вхождение i токена t_i) — (поле f, индекс слова j) с качеством q > 0
  edges(i) = [(f, j, quality(t_i, w_fj)) for f in fields, j in words(offer.norm[f]) if quality > 0]
             отсортированы по (q·weight[f] desc, порядок полей TITLE,AUTHOR,SERIES,READER, j asc)
  weight(e) = 1000 + round(100 · q · weight[f])          // мощность важнее качества
  matching = maxWeightMatching(edges, weight)           // венгерский алгоритм; слово поля (f,j) используется один раз;
                                                       // равенства — по порядку полей и индексу слова
  assigned = {i → (f, j, q)} из matching
  covered  = |{i ∈ SIG : i ∈ assigned}|; coverage = covered / |SIG|
  base     = Σ_{i ∈ assigned} q_i · weight[f_i] / |Q| · 100
  bonus    = 0
  if |Q| ≥ 2 and все assigned в одном поле f подряд и по порядку → bonus += 8
  if ∃f: key(offer[f]) == key(req.text) → bonus += 10 (один раз)
  if req содержит « — »/« - », левая часть легла в AUTHOR, правая в TITLE → bonus += 3
  s = min(100, round(base + bonus))
  tier = A if ∃f ∈ fields: key(offer[f]) == key(req.text)
       | B if coverage == 1 and all q == 1.0 and assigned подряд в одном поле
       | C if coverage == 1 and all q == 1.0
       | D if coverage == 1
       | E
  if offer.source.profile.scope == FULLTEXT and tier == E → секция «Похожие» независимо от s
  return (tier, s, assigned, reason(assigned))
quality(t, w):
  if isNumber(t) → (w == t) ? 1.0 : 0
  if w == t → 1.0
  if len(t) ≥ 4 and w.startsWith(t) → 0.9
  if |len(t) − len(w)| > 2 → 0
  if len(t) ≥ 5 and OSA(t, w) == 1 → 0.8
  if len(t) ≥ 9 and OSA(t, w) == 2 → 0.65
  return 0
maxWeightMatching(edges, weight): венгерский алгоритм (Куна–Манкреса) на прямоугольной матрице |Q| × |слова полей|,
  отсутствующее ребро — вес 0; детерминирован порядком строк и столбцов; O(|Q|² · |слова|), ≤ 12² · 96.
```

### A.3. Группировка (`SearchGrouper.group`)

```
group(offers, shownIds):                                   // shownIds: id групп, уже показанных пользователю
  for o in offers:
    (o.normTitle, o.edition) = splitEdition(o.book.name)
    o.authors = persons(o.book.autor); o.readers = persons(o.book.artist)
    o.key = (o.normTitle, sortedSet(o.authors.words))
  groups = union by equal key                               // шаг 1
  for g in groups with authors == ∅:                        // шаг 2: безавторные
    cands = [h : h.normTitle == g.normTitle and h.authors ≠ ∅]
    if |cands| == 1 → merge(g → cands[0])
  if fuzzyEnabled:                                          // шаг 3, за флагом
    buckets = map word → sorted list of groups whose author words contain word (len(word) ≥ 4)
    for word in sorted(buckets.keys):
      list = buckets[word]                                  // sorted by (normTitle, authors)
      for i < j in list:
        a, b = list[i], list[j]; skip if either merged
        if not authorsCompatible(a, b) → continue           // против объединённых авторов группы, A.1
        if dice(bigrams(a.normTitle), bigrams(b.normTitle)) < 0.92 → continue
        if numbers(a.normTitle) ≠ numbers(b.normTitle) → continue
        merge(b → a)                                        // a — лексикографически меньший ключ
  groups = [g : not g.merged]                               // поглощённые группы исчезают до озвучек и возврата
  for g in groups:                                          // шаг 4: озвучки
    g.narrations = partition(g.offers by (readerKey = sortedSet(readers.words) or "", edition))
    for n in g.narrations:
      clusters = greedy clusters by duration (sorted asc), разброс ≤ max(5 мин, 10 %);
      offers без длительности → единственный кластер, если он один; иначе кластер «неизвестно»
      n = split by clusters
    for n in g.narrations:                                  // шаг 5: зеркала
      collapse offers with same Provider.original() into one offer with mirrors=[...]
  for g in groups:                                          // идентичность
    shown = [id ∈ shownIds среди g.id и g.mergedIds]
    g.id = shown non-empty ? min(shown) : min(o.url for o in g.offers)
    g.remap = {id → g.id for id in shown \ {g.id}}           // UI: старый элемент исчезает, фокус/лист переходят
  return groups
merge(b → a): a.offers += b.offers; a.authors ∪= b.authors; a.mergedIds += {b.id} ∪ b.mergedIds; b.merged = true
```

Тест детерминизма: `group(shuffle(offers), ∅)` даёт то же множество групп (по множествам URL) для 20 перемешиваний каждого случая корпуса; тест идентичности: `group(offers ∪ late, shownIds)` для каждого id из `shownIds` либо сохраняет его, либо даёт `remap` на выжившую группу, содержащую те же предложения. Открытый лист «Озвучки и сайты» (§9.5) после пересчёта находит свою группу по URL предложения, а не по id.

### A.4. Планировщик (фрагмент)

```
plan(req, sources):
  steps = []
  families = groupBy(sources, s → s.original())
  for fam in families:
    members = fam ∩ active ∩ enabled, в порядке пользователя
    chosen = setting(oneRequestPerFamily) ? [preferred(members, req)] : members
    for s in chosen:
      p = s.parser.searchProfile()
      if len(req.text) < p.minQueryChars → steps += Skipped(s, SHORT_QUERY); continue
      path = (req.scope == {TITLE} and p.titleOnlyParam != null) ? TITLE_ONLY : BOOKS
      steps += Book(s, path, req.text, fallback = fallbackFor(p, req))
      if AUTHOR ∈ req.scope and p.peopleAuthors → steps += People(s, AUTHORS, req.text)
      if READER ∈ req.scope and p.peopleReaders → steps += People(s, PERFORMERS, req.text)
    for s in members \ chosen → steps += Skipped(s, VIA_MIRROR(chosen[0]), onFailureOf = chosen[0])
  return steps
preferred(members, req): max by (indexWidthFor(req.scope), −userOrderIndex, healthOk)
fallbackFor(p, req):                                     // приоритет §7.3; 429 обрабатывается сессией отдельно
  if req.scope == ∅ and p.scope == TITLE_ONLY and not p.ownFallback and |significant(req)| ≥ 2 → NEIGHBOUR_HINT
  if req.scope == ∅ and p.scope == FULLTEXT and p.titleOnlyParam != null and |significant(req)| ≥ 2 → NEIGHBOUR_HINT_TITLEONLY
  if p.caseSensitive → CASE_VARIANT                      // путь TITLE_ONLY области «Название» резерва не получает
  return NONE
neighbourHint(session):                                  // момент решения: конец первого прохода или 20 с
  votes = {source.original() → слова запроса, назначенные AUTHOR/READER у лучшего предложения источника}
  if |votes| ≥ 2 and доля голосов за самый частый набор ≥ 2/3 → titleWords = Q \ набор
  for s with fallback NEIGHBOUR_HINT* and result EMPTY → один запрос titleWords (путём BOOKS или TITLE_ONLY);
    карточки принимаются, только если слова набора совпали с их полем автора/чтеца (§6.2)
```
